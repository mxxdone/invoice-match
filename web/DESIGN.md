# 디자인 기준과 API 연결 경계

이 문서는 `web/` 디자인 시안의 인계 지침이다. P1-10 첫 연결 slice로 `/login`은 실제 `GET /api/me`에, `/cases` 목록은 실제 `GET /api/invoice-cases`에 연결됐다. 상세·비교 조회 slice로 실제 목록 ID의 `/cases/[id]`가 청구서 상세·비교·검토 대상·결정·감사·인계 상태 조회 API에 연결됐다(읽기 전용). 작성 slice로 `/cases/new`가 실제 생성 → 초안 저장 → 제출과 보완 revision 열기 쓰기 API에 연결됐다. 검토 slice로 `/cases/[id]`에 운영자 대사 실행과 승인자의 검토 대상 동결·매핑·보완요청·거절·승인이 실제 API로 연결됐다. `/`, `/handoff`, `/operations`는 아직 시안이며 P1-10 인수는 완료되지 않았다.

## 화면

| 경로 | 화면 | 현재 시연 |
|---|---|---|
| `/login` | 로그인 | 실제 로그인. 자격증명은 React 메모리에만 보관하고 `/api/me`로 서버 판정 |
| `/cases` | 사건 목록 | 실제 서버 페이징·부분 검색·AND 필터 목록. URL에 필터를 보존해 상세 왕복 시 복원. 행/요약에서 실제 사건 ID 상세로 이동 |
| `/cases/[id]` | 청구서 상세·비교·검토 | 실제 조회 + 역할별 동작. 운영자 대사 실행, 승인자 검토 대상 동결·매핑·보완요청·거절·승인. 자기 승인은 서버가 거부 |
| `/cases/new` | 청구 작성·수정 | 실제 생성 → 초안 저장 → 제출. `?case=` 초안 편집과 `?supplement=` 보완 재작성(새 revision 열기)을 서버 계약으로 처리. 합계는 확인용 |
| `/` | 청구서 상세·검토 시안 | 비교표·행 근거·사유 모달·감사 탭, 정상·다섯 예외 예시. 루트 시안은 그대로 유지 |
| `/handoff` | ERP 인계 상세 | 결과불명·인계 완료·실패의 상태 배치 |
| `/operations` | 운영 작업 | 대사 대상·인계 실패·결과불명 목록과 근거 패널 |

`/login`, `/cases`, `/cases/[id]`는 실제 서버 계약(`/api/me`, `/api/invoice-cases`, 상세 조회 API)을 사용한다. `/cases/new`, `/`, `/handoff`, `/operations`의 계정·사건·금액·시간·식별자는 가상 시안이다. 사이드바의 '디자인 시안' 안내 문구와 가상 계정 표기는 시안 화면에만 표시하고 실제 화면에는 표시하지 않는다. 디자인용 탐색 메뉴는 모든 역할의 화면을 노출하지만 실제 권한을 구현한 것으로 간주하지 않는다.

## 실제 상세 조회 연결 범위 (P1-10 상세 slice)

- 역할 경계는 서버가 결정한다. `SUBMITTER`는 자기 청구만, 승인자·운영자는 모든 청구를 조회한다. 권한 없는 보조 조회(대사·검토·감사)는 요청 자체를 보내지 않고 `403` 안내로 대체한다.
- 연결한 조회: `GET /api/invoice-cases/{id}`, `.../evidence-bundles`(와 필요 시 `.../evidence-bundles/{version}`), `.../match`, `.../review-snapshots/latest`, `.../review-snapshots/{number}/freshness`, `.../review-decisions`, `.../audit-entries`, `.../handoff`.
- 서버가 제공하지 않는 값(공급사명, 총액, 검수 재고, 매핑 후보, 현재성 판정)은 UI가 만들지 않는다. 승인 금액은 `handoff.payment.amount`가 있을 때만 서버 값으로 표시한다.
- 사건 자체의 `404`와 섹션 자료 없음(미대사·미 snapshot 등)을 구분한다. 작성 중 draft가 없으면 제출 시점 라인은 최신 동결 증빙 본문에서 읽는다.
- 검토 최신성은 서버의 `current`/`reasons`를 그대로 표시하고 UI가 재판정하지 않는다. 버전·해시는 기술 정보 펼침으로 확인한다.
- 비교 결과는 어떤 증빙 version으로 계산됐는지 명시한다. 현재 최신 증빙 version과 다르면 `이전 제출자료 기준 비교 결과(오래된 결과)`로 구분하고 서버 정상 판정은 `당시 자료 서버판정`으로만 표시한다. 숨기지 않는다.
- 금액·단가는 서버 `long`이다. JavaScript 안전 정수(2^53−1)를 넘는 값은 정확히 표현할 수 없으므로 `지원 범위 초과 (정확 표시 불가)`로 표시하고 정확한 값처럼 포맷·연산하지 않는다. exact integer/문자열 계약이 필요하면 backend 변경이므로 Head 승인 대상이다.
- 승인·매핑·보완·거절 쓰기는 상세 화면에 아직 연결하지 않았고, 버튼은 비활성 상태와 미연결 안내만 표시한다. `/backend` 프록시는 GET 경로와 함께 쓰기 경로를 exact method+path로만 허용하고(UUID/번호 패턴 검증), 요청 body는 서버와 동일한 256 KiB로 stream 제한하며 초과 시 `413`, deadline 초과 시 `504`, 연결 실패 시 `503`을 반환한다. redirect는 따르지 않고 모든 응답은 `no-store`다.

## 실제 작성 쓰기 연결 범위 (P1-10 작성 slice)

- `/cases/new`는 `POST /api/invoice-cases`(생성), `PUT .../{id}/draft`(초안 교체), `POST .../{id}/submit`(제출 동결), `POST .../{id}/revisions`(보완 revision 열기)를 사용한다. 생성·초안 저장·제출은 서버의 별도 원자 작업이며 단계별 성공/실패를 화면에 구분한다.
- 생성이 성공하고 초안 저장이 실패하면 같은 사건을 재사용한다. 새 사건을 무조건 다시 만들지 않는다. 같은 intent의 재시도는 같은 `requestId`와 정확히 같은 payload를 보내고, 입력이 바뀌거나 version이 갱신되면 새 `requestId`를 쓴다.
- 응답이 유실된 불명확한 실패(네트워크/5xx/timeout)는 자동 재전송하지 않고 결과 미확정으로 안내한다. 재시도는 동일 intent로만 수동 수행한다. 409는 서버 코드·메시지를 그대로 보여주고 최신 청구서를 다시 조회한 뒤 사용자가 다시 확인·저장·제출한다. 서버 금액·판정을 UI가 재계산하지 않는다.
- 작성 중 화면 이동은 서버 반영을 취소하지 않는다. 미확정 작업·입력 유실 가능성을 안내하고 `beforeunload` 경고를 표시한다. 자격증명·요청 payload는 저장소에 남기지 않는다.
- 보완 수정에서 사건 헤더는 편집 대상이 아니다. `SUPPLEMENT_REQUIRED`일 때만 보완 revision을 열고 제출한다. 초안 편집은 `DRAFT`일 때만 가능하다.
- 확정 품목 ID는 선택 입력이며 품목 매핑 후보 조회·자동 매핑·원본 파일 접수는 제공하지 않는다. 서버에 없는 공급사명·원문·PDF·AI·재송신·lookup 기능을 만들지 않는다.

## 실제 검토 쓰기 연결 범위 (P1-10 검토 slice)

- 운영자는 `POST .../match`로 대사를 실행하고, 승인자는 `POST .../review-snapshots`(동결), `POST .../mapping-decisions`(매핑), `POST .../supplement-requests`(보완요청), `POST .../reject`(거절), `POST .../approve`(승인)를 사용한다.
- 모든 결정은 화면에 표시한 `reviewSnapshotId`·`reviewPayloadHash`·청구서 `expectedCaseVersion`으로 기록한다. 승인 요청에는 증빙 bundle version을 별도로 싣지 않는다(동결 근거는 snapshot이 가지며 서버가 재검증). `decidedBy`는 보내지 않는다.
- 결정 성공 시 응답을 로컬 반영하지 않고 사건을 다시 조회한다. 409(경합·stale)는 서버 코드·메시지를 표시하고 최신 자료를 다시 조회한 뒤 사용자가 재확인한다(자동 재계산·자동 승인 없음).
- 매핑은 서버 대사 결과의 라인과 `itemId` 수동 입력으로만 수행한다(후보 조회 API 없음). 서버가 유일한 PO 라인으로 검증한다.
- 자기 승인은 UI가 차단하지 않고 서버 응답으로 거부 사유를 표시한다. 금액·판정·권한은 서버 값만 표시한다.
- 인계 완료(ACK)는 ERP 인계 완료를 뜻하며 송금 완료가 아니다. 결과불명에 자동 재전송 버튼을 두지 않는다.

## 유지할 디자인

- Ramp의 기본 표 프레임을 참고한 따뜻한 회색 사이드바, 흰 본문, 얇은 경계, 올리브 텍스트와 라임 포인트.
- 로고, 토큰, 탭, 표, 버튼, 패널은 공유한다. `globals.css`는 기본 토큰·상세, `screens.css`는 나머지 배치, `ui.tsx`는 공통 요소다.
- 카드 대시보드·새 테마·그래프·AI 채팅으로 임의 변경하지 않는다.
- 실제 데이터로 넘침·줄바꿈이 생기면 기능 Worker가 임의 재설계하지 말고 Head의 시각 검증을 요청한다.

## 후속 Worker가 구현할 경계

- 상세 조회는 실제 DTO와 view model로 연결됐다. 남은 시안(`/cases/new`, `/`, `/handoff`, `/operations`)의 고정 fixture는 실제 계약으로 교체한다. 시안 데이터는 서버 DTO가 아니다.
- 역할·소유권·자기승인·최신성·idempotency를 실제 계약에 맞춰 처리한다. 실제 상세 화면은 401/403/404와 섹션 데이터 없음·오류·로딩을 이미 구분한다. 남은 쓰기 흐름은 409(경합·stale)를 추가로 처리해야 한다.
- 일반 목록 DTO에 없는 합계·예외 상세를 별도 API 없이 추측하지 않는다. 목록 제출 시각은 `submittedAt`이며 작성 중에는 없을 수 있다.
- 운영 목록의 오류 요약은 현재 가상이다. 실제 handoff 조회와 결합할 때 N+1·집계 계약을 검토하고 필요한 변경은 별도 승인받는다.
- 작성 API는 사건 생성 → draft 저장 → 제출 흐름이다. 입력 합계는 확인용이며 서버를 대체하지 않는다.
- 보완 수정에서 사건 헤더는 편집 대상이 아니다. 실제 상태가 SUPPLEMENT_REQUIRED일 때 새 revision을 열고 제출한다.
- 검토는 화면에 표시한 동일 frozen subject version/hash를 사용하고 매핑 후 successorSnapshot을 반영한다.
- 지급 상태는 서버 값을 표시한다. 인계 완료를 송금 완료로 바꾸거나 결과불명에 재전송 버튼을 추가하지 않는다.
- 인증 시연을 실제 로그인 성공으로 취급하지 않는다. 비밀번호 저장·로그 기록을 금지한다.
- PDF/AI/RabbitMQ/DLQ는 이후 Phase다. 지금 구현된 것으로 화면에 넣지 않는다.

UI 디자인 파일만으로 Ticket 완료를 선언하지 않는다. 실제 업무 흐름·권한·경합·stale 검증 후 Head가 인수한다.

## 디자인 감사 후 검수 항목

- 상세: 매핑 후보 선택과 후속 검토 표시, 기록된/빈 결정 이력, 감사 변경 상세, 오래된 검토 대상·자기 승인·운영자 읽기 전용 상태.
- 목록: 제출자·제출일 필터와 페이지 이동. 공급사·상태 필터와 검색 유지.
- 목록 개선: 회사명 앞 두 글자(로고 없을 때)와 공급사별 동일 색, 상태 의미별 색상, 기본 20건 및 20/50/100 선택, 번호형 페이지 이동. 회사명은 가상 데이터이며 현재 목록 DTO에는 없으므로 연결 시 실제 공급사명 제공 경로를 확인하고 없으면 ID/기본 아이콘으로 표시한다.
- 검색은 청구번호/발주번호 선택 후 Enter 또는 버튼으로 적용하며 필터 변경·검색·표시수 변경 시 1페이지로 이동한다. 부분 검색은 사용자 승인된 변경이고 별도 backend Worker가 구현 중이다. invoiceNumber 정규화 후 포함, PO 대소문자 무시 포함, 공급사/제출자 정확 조건 유지. 시안의 로컬 필터를 실제 페이지 일부만 필터링하는 방식으로 연결하지 않는다.
- 공통: 로딩·데이터 없음·조회 실패·401·403 배치. 상태 선택기는 디자인 검수용이며 최종 서비스 UI에서 제거한다.
- 목록의 처리기한·예외 유형 요약은 현재 조회 계약에 없으므로 미표시. 요구사항/API 차이는 연결 단계의 확인 사항이며 임의 계산·새 백엔드 구현을 하지 않는다.
- 이 감사는 디자인 범위다. 실제 인증, cursor 조회, idempotency, 최신성 재조회 및 업무 상태 전이는 API 연결 후 검증한다.

## 후순위 디자인 작업

- 사용자 요청: 현재 연두색 주요 버튼이 다소 튀므로, 감사 완료 뒤 채도를 낮춘 세이지·올리브 계열 후보를 동일 화면에서 비교한다.
- 기존 테마는 후보 확인 전 변경하지 않는다. 일반/hover/disabled/focus 상태와 글자 대비, 다른 버튼과의 식별성을 함께 검수한다.
