# 테스트와 자원 운영 절차

빌드·실제 서비스 검증·자원 정리가 필요한 작업에서만 읽는다. 제품 기준은 `Spec.md`, 현재 작업 계약은 `Plan.md`, 공통 작업 규칙은 루트 `AGENTS.md`에 있다.

## 검증 범위

- 개발 중에는 변경 범위의 focused 테스트를 먼저 실행한다. Ticket에서 요구한 전체 검증과 실제 DB·저장소·broker 검증은 생략하거나 mock으로 대체하지 않는다.
- 백엔드 테스트는 로컬 Java로 실행하고 필요한 의존 서비스만 Docker로 띄운다. 전체 Compose 빌드는 서비스 간 연결·배포 구성 검증에 필요할 때만 수행한다.
- 코드·의존성·Dockerfile이 바뀐 서비스의 기존 이미지를 최신 검증 근거로 사용하지 않는다. 성공한 검증은 새 변경이나 미해결 우려가 없는 한 반복하지 않는다.
- 명령은 live log와 제한 시간을 적용한다. 절차가 반복되면 시작·준비 확인·검증·실패/중단 cleanup을 재사용 스크립트로 묶는다. 정리 실패도 실패로 보고한다.

## 소유 자원 정리

- 실행별 PID·포트·project/container/volume/image와 용도를 기록한다. 테스트 데이터와 사용자·시연 데이터를 구분한다.
- 성공·실패·중단 후 자신이 만든 임시 자원을 정리하고 잔류를 확인한다. Testcontainers 자동 정리만으로 완료를 주장하지 않는다.
- Compose 검증은 고유 project로 격리하고 `finally`에서 해당 자원만 회수한다. `down -v`는 버려도 되는 검증 volume에만 사용한다.
- 사용자 서비스·시연 DB·공유 이미지·다른 실행 자원은 보존한다. 소유권 확인 없는 전체 prune, volume 삭제, Docker 초기화, 가상 디스크 직접 삭제는 금지한다.
- 임시 검증 이미지는 사용 여부를 확인해 정리하되 PostgreSQL·Node 등의 재사용 기반 이미지는 유지한다. 남겨 둔 자원은 주소·상태·목적·종료 방법을 보고한다.
- 빌드 완료 뒤 shell이 반환되지 않으면 own process/session을 진단한다. 원인 확인 없이 같은 명령을 반복하거나 사용자 프로세스를 종료하지 않는다.
- 로그에 credential을 남기지 않는다. 검증 로그·스크린샷은 ignored `output/`에 보존하며 Spec/Plan에 실행 경과를 복제하지 않는다.

## 이 개발 PC의 디스크 관리

- 큰 빌드·전체 검증 전에 C/D 여유 공간과 `docker system df`를 확인한다. C 여유 5GiB 미만이면 큰 빌드를 시작하지 않고 원인을 확인한다.
- workspace가 D에 있어도 TEMP·도구 캐시·Docker 데이터는 C에 쌓일 수 있다. 사용 중인 캐시는 지우지 않고 임시 경로·캐시를 D에 두는 실행 설정을 우선한다.
- Docker 빌드 캐시 보관 목표는 2GB다. 인수 후 또는 공간 부족 시 활성 빌드가 없는지 확인하고 설치 CLI의 `--help`로 옵션을 확인한 다음 `docker buildx prune --all --max-used-space 2GB`를 사용한다. 공유 캐시 정리는 다른 실행과 조율한다.
- npm 다운로드 캐시는 재생성 가능하지만 활성 npm/npx 캐시와 `_npx` 실행파일은 보존한다. 도구·Docker 저장 경로 이전은 공식 설정과 데이터 보존·재기동 검증으로 수행하며 임의 파일 이동은 하지 않는다.
- 정리 전후 호스트 여유 공간과 Docker 사용량을 기록한다. 공유 레이어를 중복 합산하거나 내부 정리량을 실제 C 회복량으로 간주하지 않는다.
